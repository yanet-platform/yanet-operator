# v4.0.0 — persistent gateway policy with upstream reload

The operator image and Helm chart are both `4.0.0`. This major release replaces
the managed gateway policy delivery and offline-startup contract. The Kubernetes
API remains `yanet.yanet-platform.io/v1alpha1`.

## What changed

- Every managed gateway uses file-based authorization. A stable ConfigMap per
  installation/Node feeds `policy-sync`, which atomically replaces individual
  identity, permission and optional SSH CA files in a persistent directory shared
  by that Node's gateway instances.
- Account and grant changes preserve existing gateway `Deployment.spec` and do
  not require a gateway rollout, certificate issuance or a workload update window.
- TLS delivery remains separate: `credential-sync` handles certificates and
  `policy-sync` handles public gateway policy. Saved files support offline restart.
- The previous policy exporter, revision/checkpoint handoff and mode-selection
  protocol are removed. There is no in-place migration.
- SSH trust is read once per policy plan and reused across its Node projections.
- Pull-request Docker jobs build without publishing images.

## Runtime requirements and behavior

Use a runtime containing upstream
[identity file reload](https://github.com/yanet-platform/yanet2/pull/3549) and
[permission file reload](https://github.com/yanet-platform/yanet2/pull/3552).
Configure the exporter with a digest-pinned `4.0.0` operator image containing
both `/manager credential-sync` and `/manager policy-sync`.

Identity and permissions refresh independently every five seconds after files
reach the Node. There is no cross-file generation or monotonic revision guarantee.
New RPCs use refreshed policy, including on existing TLS connections; open streams
continue. A reload error retains the affected source's last valid data.

Grants come from wired client profiles' `gatewayPermissions` and
`additionalGatewayAccounts`. Disabling a client does not revoke its grants.
Deleting `ssh-ca.pub` does not revoke an already loaded SSH CA; remove accounts or
permissions to deny new RPCs.

## Clean replacement

1. Stop the old managed workloads and retire their offline startup definitions
   so they cannot restart with the previous delivery contract.
2. Prepare the compatible runtime and digest-pinned `4.0.0` exporter images,
   native authentication configuration, issuer and trust sources.
3. Create a clean managed installation using the current CRDs and configuration.
   Do not adopt the old policy checkpoints or reuse the old installation's
   persisted policy as the new installation's startup state.
4. Wait for TLS and policy delivery, verify allowed and denied new RPCs, and
   refresh the site's offline startup definitions using the new persistent paths.

See [managed workload certificates and gateway policy](../MANAGED_CERTIFICATES.md)
for configuration, storage ownership and startup details. This is a coordinated
replacement, not a rolling upgrade or compatibility handoff.

## Known limitation

If a configured SSH trust ConfigMap is missing or invalid, resource preflight
also blocks independent dataplane creation, image updates and component-only
scale-to-zero on selected Nodes until the source is repaired. Existing dataplane
processes continue running; whole-installation disable and released-Node cleanup
remain available.
