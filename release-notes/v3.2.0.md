# v3.2.0 — gateway recovery and node handoff

The operator image and chart are both `3.2.0`. The `Yanet` and `YanetConfig` CRD
schemas are unchanged from `3.1.0`; there is no CRD replacement or API conversion
for this upgrade. Keep existing Helm values and do not enable certificate management
or install a second cert-manager just to upgrade.

## Before upgrading from v3.1.0

1. **Check the gateway listener on every active Node/NUMA instance.** For a
   HostPath controlplane without a managed server profile, the native configuration
   now owns its listener. If the Service relied on the old implicit plaintext
   bind, explicitly configure its existing transport on a Pod-reachable address
   and Service target (normally `[::]:8080`). For an external TLS-only gateway,
   keep the TLS bind and leave the plaintext endpoint unset or empty. Verify the
   intended transport through both Pod IP and Service before replacing workloads.
2. **If using managed credentials**, upgrade the manager and pin
   `YanetConfig/config.spec.certificates.exporterImage` to the `3.2.0` release
   image digest (or a verified mirror). Preserve role paths, native configuration,
   current SSH CA bytes, accounts and grants. Keep issuer/approver restrictions;
   verify that the deployed cert-manager reports `Ready` for the current generation.
   If certificate management is off, no exporter or checkpoint ACK is needed.
3. **For each installation with a managed gateway**, wait for the current-generation
   rollout of all revision-aware writers and gates. Replace and verify every supported
   offline checkpoint, including each active NUMA gateway. Only then set the
   `yanet.yanet-platform.io/policy-checkpoints-ready` annotation on the `Yanet` to
   the verified `<installation-UID>/<revision>`. Wait for `policy-state.activated`
   to become `true` before changing policy. Membership or revision changes require
   repeating verification. Retire pre-protocol checkpoints after activation.
4. **When handing off Nodes**, keep selectors and hostname labels stable during
   drain. Workloads now use required affinity on the exact Node name. Old ReplicaSets
   and terminating Pods can still hold a claim. Verify that old replicas have drained,
   Pods have exited and offline workloads cannot restart on that Node before handing it over.

## What changed

- An external TLS listener is preserved. The Helm manager no longer receives the
  dedicated webhook certificate job's Secret permissions.
- A writer verifies the CA actually delivered to a role and confirms durable
  readiness. A delayed certificate or SSH projection does not overwrite active trust
  or block independent roles from making progress. The offline startup check stays read-only.
- The controller validates the final Pod before applying resources and no longer
  treats a new Deployment template as proof that the old Pod has released its Node.
- The release workflow accepts annotated release tags after shallow checkout.

## Rollout and rollback gates

Qualify the exact runtime images and effective configuration with allowed and
denied RPCs, rotation/reconnect and offline cold start. Confirm ACL freshness
independently of leaf validity. Kubernetes readiness does not attest to external
checkpoint contents. If these checks fail, hold the rollout. A direct manager
downgrade or restoring a historical `current` is not a supported shortcut after
policy activation. Before restoring grants on rollback, verify supported checkpoints
under the target CA with restrictive grants.

See the [migration, inspection and rollback runbook](https://github.com/yanet-platform/yanet-operator/blob/v3.2.0/MANAGED_CERTIFICATES.md#policy-handoff-and-upgrade-from-v310)
and the [listener preflight](https://github.com/yanet-platform/yanet-operator/blob/v3.2.0/MANAGED_CERTIFICATES.md#gateway-listener-preflight-for-upgrades-from-v310).
